# 백업 / 원복 규칙

모든 에이전트(오케스트레이터 포함)가 반드시 준수한다.

## 원칙

- 수정 전 백업, 문제 시 원복, **원복 시 owner 승인**
- 백업 없는 수정은 금지
- 백업했다고 주장하는 것과 백업된 것은 다르다 — **검증한다**

## 파일 변경

```bash
# 0. 백업 디렉토리 확보
mkdir -p /opt/backup/{app}

# 1. 백업 (웹루트 밖에 저장)
BAK=/opt/backup/{app}/$(basename "$FILE").bak_$(date +%Y%m%d%H%M%S)_${AGENT_NAME}
cp "$FILE" "$BAK"

# 2. 검증 — 이 단계를 건너뛰면 백업 없는 수정이 발생한다
[ -s "$BAK" ] || { echo "백업 실패 — 작업 중단"; exit 1; }

# 3. 수정 진행
```

### 파일명에 초(`%S`)와 에이전트명을 붙이는 이유

분 단위 타임스탬프만 쓰면 같은 파일을 1분 안에 두 번 수정할 때
**앞선 백업이 덮어써진다.** 여러 에이전트가 동시에 도는 환경에서는 실제로 발생한다.

### 웹루트 안 백업 금지

`/var/www/{app}/` 등 웹루트 내부에 `.bak_` 파일 생성 **절대 금지**.

`.bak_` 파일은 웹에서 그대로 접근 가능하다. 소스코드와 키 정보가 노출된다.

> 2026-03-30 보안 점검에서 웹루트 내 노출 백업 파일 **104개** 발견.
> 이 규칙은 그 사고 이후에 만들어졌다.

## DB 변경

| 작업 | 권한 |
|------|------|
| `SELECT` | 자유 |
| `INSERT` / `UPDATE` / `DELETE` | **owner 확인 후** |

- 트랜잭션 사용: `BEGIN` → 작업 → `COMMIT` (문제 시 `ROLLBACK`)
- 대량 변경: **영향 행 수를 먼저 `SELECT`로 확인**한 뒤 진행

## 크론 / 설정 변경

```bash
# crontab
crontab -l > /opt/backup/{app}/crontab_$(date +%Y%m%d%H%M%S).txt

# 설정 파일 (웹루트 밖)
cp "$CONF" /opt/backup/{app}/$(basename "$CONF").bak_$(date +%Y%m%d%H%M%S)
```

## 원복 절차

1. 문제 감지
2. **현재 상태를 먼저 백업** — `*.broken_$(date +%Y%m%d%H%M%S)`
3. owner에게 보고 + 원복 승인 요청
4. 승인 후 백업에서 원복
5. 원복 결과 검증
6. 보고

### 2번을 건너뛰지 않는다

바로 덮어쓰면 **문제가 있던 상태가 사라진다.**
왜 깨졌는지 분석할 근거가 없어지고, 같은 사고가 반복된다.

### 3번을 에이전트가 생략하지 않는다

원복은 에이전트가 단독 판단으로 실행하지 않는다.
에이전트가 임의로 되돌리기 시작하면 무엇이 진짜 현재 상태인지 아무도 모르게 된다.

## 보관 기간

| 대상 | 보관 | 비고 |
|------|------|------|
| 일반 백업 | 30일 | 주기적 정리 |
| `*.broken_*` | 90일 | 사후 분석용, 길게 보관 |
| 크론 / 설정 | 90일 | |

정리 규칙이 없으면 백업 디렉토리가 무한히 커지고,
디스크가 차는 순간 백업 자체가 실패하기 시작한다.
