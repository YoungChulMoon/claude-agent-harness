# 예측 결과로 결론·코딩 금지

전 에이전트 + 오케스트레이터 필수.

> **상대방(오케스트레이터·타 에이전트·타 시스템)의 결과를 "이렇게 나올 것"이라고 예측·가정해서
> 결론 내리거나 그 위에 코딩하지 마라.**
> 반드시 **실제 결과를 받고 검증한 뒤** 다음 단계로 진행한다.

## 왜

- 예측은 빗나간다. 빗나간 가정 위에 쌓은 결론·코드는 전부 재작업이다.
- "타 팀이 푸시했겠지" / "그 API가 이 필드를 줄 거야" / "오케가 X를 넘겨줬을 거야"
  — 전부 **검증 대상**이지 사실이 아니다.
- 기존 코드·데이터 추론 금지 규칙의 **크로스시스템 확장판**.
  기존 코드뿐 아니라 *다른 주체가 만들거나 넘길 결과*도 추론 금지.

## 금지 (예측 위 진행)

- 타 팀/타 시스템이 "했다고 말한" 작업을 실측 없이 사실로 간주
- 받지 않은 API 응답의 스키마·값을 가정하고 그 위에 파싱·분기 코딩
- 오케/타 에이전트가 넘길 결과물(SQL·파일·패키지·커밋)을 미수령 상태에서 완료로 간주
- "당연히 이렇게 돌 것" 추론으로 후속 단계 선코딩

## 의무 (실측 후 진행)

1. 의존하는 결과는 **실제로 받는다** — 응답·파일·커밋·로그·DB 행을 눈으로 확인
2. 받은 결과를 **검증한다** — 존재·스키마·값·상태
3. 검증 통과 후에만 결론·다음 코딩
4. 결과가 아직 없으면 → **대기/관찰(Open)로 둔다.** 가정으로 진행 X

4번이 실무에서 가장 어렵다.
"일단 이렇게 되겠거니 하고 진행"이 자연스럽게 느껴지기 때문이다.
Open으로 남기는 것이 진행보다 나은 상태라는 것을 규칙으로 못 박아야 지켜진다.

## 사례 (2026-06-26)

타 팀이 검색 API를 "푸시했다"고 보고했으나 실제로는 미푸시 상태였다.
가정 위에 배포를 진행했으면 깨졌을 것이다.

→ 팀이 미푸시를 인정한 뒤, 실제 푸시와 실측(인덱스 **11,059건**)을 확인하고서야 배포를 진행했다.

## 연계

- 기존 영역 추론 금지 규칙 — 본 룰은 그 크로스시스템 확장
- 크로스팀 전달 사이클 — 4단계 전달, 수령 확인
- 사후 검증 규칙 — 서술을 만들 때 실측 검증 후에만 라벨링
