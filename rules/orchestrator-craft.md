# 오케스트레이션 실증 패턴 9개

모델 불문 적용. 전 에이전트 + 오케스트레이터 필수.

2026-07-16 세션에서 실증된 작업 절차다.
(하네스 보안검토 → 도구 SoT 정립 → 에이전트 통폐합 **22→17** → 트리아지 Open **148→131**)

모델 종류와 무관한 **절차 규칙**이다. 어떤 모델이 세션을 돌든 이대로 일한다.
기존 규칙(결과 예측 금지 · 기존 확인 · 백업/원복 · 작업 로그 · 도구 등재)의 **실행법**이며 대체가 아니다.

## 어떤 문제를 겪고 있는가

| 증상 | 패턴 |
|------|------|
| 컨텍스트가 금방 찬다 | §1 배치 실측 |
| 같은 문제가 계속 재발한다 | §2 배선 진단 |
| 여러 에이전트가 같은 파일을 건드려 깨진다 | §3 판정/집행 분리 |
| owner 확인 대기로 계속 멈춘다 | §4 판단대기 압축 |
| 에이전트가 제약을 우회하려 한다 | §5 차단 대응 |
| 보고는 성공인데 실제로는 안 고쳐져 있다 | §6 정직 기록 · §7 재검증 |
| 만든 규칙을 아무도 안 지킨다 | §8 dogfooding |
| 조사가 너무 느리다 | §9 병렬 기본기 |

## 1. 실측은 배치로 한 번에

- 조사는 배치 실행 **1~2회**로 광범위 수집 → 그 위에서 판단.
  개별 조회를 연쇄하며 컨텍스트를 태우지 않는다.
- 민감값이 판단에 필요하면 **값 비노출 대조**로 설계한다.
  (예: 비밀번호는 일치 여부만 출력하고, 값 자체는 컨텍스트에 올리지 않는다)

## 2. 증상이 아니라 배선을 진단한다

반복되는 문제("보고를 못 받음", "같은 도구를 계속 재발명함")는
개별 건을 처리하기 전에 **구조 결함**을 의심한다.

- pull-only 배선
- SoT(단일 진실 원천) 부재
- 종결 게이트 부재

처방도 구조로 한다: **SoT 신설 + push 채널 + 등재=종결조건 게이트.**

> 실증: 관찰 보고가 세션 훅 pull 단일 구조였다. 크론 push로 전환하자
> **방치되어 있던 132건이 즉시 드러났다.** 개별 건을 아무리 처리해도 보이지 않던 것들이다.

## 3. 판정과 집행을 분리한다

| | 방식 | 이유 |
|---|------|------|
| **검증 · 조사** | 읽기 전용 서브에이전트 **병렬 팬아웃** | 속도 |
| **파일 · DB 집행** | 오케스트레이터 **중앙 직렬** | 충돌 방지 |

- 서브에이전트에는 도메인별로 묶어 위임하고, **"수정·쓰기 금지"를 명시**하고, 반환 포맷을 지정한다.
- 집행은 오케스트레이터가 결과를 받아 **일괄 반영**한다.
  공유 파일(인덱스 등)을 여러 에이전트가 동시에 수정하면 반드시 깨진다.

> **트레이드오프**: 대규모 스윕에서 중앙 직렬은 병목이 된다.
> 느려지는 것을 알면서도 충돌보다 낫다고 판단한 결과다.
> 집행 대상이 서로 완전히 독립된 영역이라면 부분 병렬화를 검토할 수 있다.

## 4. 기계처리와 판단대기를 가른다

- **판정 불요건**(형식 정합 · 이관 · 백필)은 즉시 기계 처리.
- **판단 필요건**은 아래 형식으로 정리해 owner의 결정을 **1줄로 압축**한다.

```
1. {건명}  ⭐추천: A
   A) {옵션}  ← 권장
   B) {옵션}
2. ...
```

"A로 전부"라는 한 줄로 끝낼 수 있게 만든다.

> **임의 종결 · 임의 결정 금지. 추천은 기계가, 판정은 사람이.**

## 5. 차단 · 거절 대응 프로토콜

**정당한 차단**(승인 범위 밖, 상주 작업 등)
→ 수용. 해당 단계만 보류하고 **나머지는 계속 진행**. 말미에 승인 요청.

**오판으로 보이는 차단**
→ **임의로 우회하지 않는다.**
근거(승인 존재 여부, 안전 영향 실측)를 정리해 보고 → 1줄 확인 후에만 진행.

> **몰래 우회 절대 금지.**

**차단 자체가 규칙 결함을 드러내는 경우**
→ 그 결함을 고치는 것까지가 대응이다.

> 이 §5 자체가 그렇게 만들어졌다. 차단을 겪고 나서 생긴 규칙이다.

## 6. 정직 기록

- owner 지시로 종결하는 건이라도 **실측 상태를 그대로 기입**하고 **재오픈 조건을 명기**한다.
- **FAIL을 PASS로 쓰지 않는다.**
- 보고는 Before/After 실측 수치로. **잔여와 리스크를 성과보다 먼저.**

> 실증 표기 예: "재발 잔존. 구버전 소멸 대기 중. 재악화 시 재오픈."

## 7. 변경 직후 1회 재검증

모든 수정 직후 즉시 실측 확인한다.

| 대상 | 확인 방법 |
|------|-----------|
| 훅 | 실행해서 출력 확인 |
| 데이터 | 카운트 재조회 |
| push | 원격 해시 대조 |

> **재검증 없는 "완료" 보고 금지.**

**배치 처리 시**: 전건 재검증은 비현실적이다.
전수 카운트 대조 + **랜덤 3건 실물 확인**으로 갈음한다.
카운트만 맞고 내용이 깨진 경우를 잡기 위해서다.

## 8. 새 규칙은 그 자리에서 자기 준수 (dogfooding)

규칙이나 도구를 만들면 **같은 세션에서 스스로 등재하고 준수한다.**

> 실증: 도구 등재 규칙을 신설한 직후, 그 세션에서 만든 도구 3종을 즉시 등재 목록에 올렸다.

다음 세션으로 미루면 그 규칙은 죽는다.

## 9. 병렬 · 스크래치 기본기

- 의존 관계가 없는 도구 호출은 **동일 메시지에 병렬로** 넣는다.
- 일회성 스크립트는 스크래치 영역에서 만든다. 재사용이 확정되면 **승격 + 등재**한다.
- 대형 스윕은 워크플로 팬아웃을 **능동적으로 제안**한다. (실행은 owner opt-in)
